4. Build in phases:

## Documentation Standard

Each project README should include:

1. Problem statement and business goal
2. Target users and primary workflows
3. Functional and non-functional requirements
4. Proposed stack and architecture overview
5. API/data modules (if applicable)
6. Setup and run instructions
7. Testing checklist
8. Future enhancements

Recommended project layout:

```text
project-name/
├── README.md
├── prompt.md            # optional, recommended
├── src/
├── docs/                # optional
└── tests/               # optional
```

## Quality Gates

Before marking any project complete, verify:

- Build and run steps are reproducible
- Core happy path and major edge cases work
- Validation and error handling are present
- Role-based access is enforced where needed
- README is accurate, current, and actionable

## Execution Roadmap

1. Domain-first sequencing:
   - System Design for architecture thinking
   - Full Stack for implementation depth
   - Cloud for deployment and operations
   - AI/ML for applied intelligence layers
2. Deliver each project as an independently runnable unit.
3. Maintain release-ready README quality in every folder.
4. Revisit completed projects for refactoring and portfolio polish.

## Repository Policies

- Folder naming: kebab-case only
- Independence: each project should run in isolation
- Scope ownership: dependencies remain local to project folders
- Documentation-first changes: update README when behavior changes
- Domain duplication allowed only when implementation context differs
